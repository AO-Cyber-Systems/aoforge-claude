# TRD 32-01: A state nothing judged stops reporting pass

<objective>
Close AO-Cyber-Systems/aodex#485's headline defect: `flutter-ui-eval.cjs:328` resolves a
`state_id` absent from `labels.json` to `{ is_broken: false }`, which scores `pass`, which
(per verifier.md Step 8c) removes the surface from the human-verification queue. 34 of 40
"passing" states were never judged by anything.

This TRD makes an unlabelled state resolve to `review`, bucketed separately from genuine
judge-disagreement reviews, and excluded from the flake budget so a single unjudged state
cannot slide through as `pass-with-reviews`.

Resolved intent: kind=plugin, work=bugfix, tdd=strict (CLAUDE.md user playbook),
depth=comprehensive, fixture_strategy=generators. Constraints honored: no_llm_test_data
(hand-built temp manifests + the checked-in fixtures), no_property_based_default
(descriptive named cases), no_gherkin_layer.
</objective>

<gotchas>
- **`validateJudgeResult` requires `confidence`, `matches_expected`, `samples` and `votes`
  to be present and correctly typed.** If you signal "unjudged" by omitting fields, the
  result fails validation and lands in the generic `judged.valid === false` branch, which
  already produces `review` — but with a validation-error advisory that reads like a bug,
  not like "nothing judged this". Carry an explicit marker instead (e.g. an `unjudged: true`
  property on the judge result, or a distinct return contract) so the CLI can route it to a
  purpose-built advisory. Whatever you choose, U4 must be able to tell the two apart.
- **The flake budget is the trap.** `scoreRun` escalates only when
  `reviews.length > flakeBudget`, and `flakeBudget` defaults to 1. If unjudged states are
  pushed into `reviews[]`, a manifest with ONE unjudged state rolls up `pass-with-reviews`
  — and #485 happens again at N=1. The flake budget exists for judge nondeterminism, not
  for absence of judgment. Keep the buckets separate.
- **Do not change verdicts for labelled states.** R1 is the guard. If a dogfood case for a
  labelled state changes, you have over-reached.
- Adding a state to the checked-in `__fixtures__/flutter-ui-eval/manifest.json` will break
  dogfood Case DF3 (`counts.pass === 1`, `counts.fail === 1`). **Build U1's manifest in a
  temp dir inside the test instead** — hermetic, and it leaves the shared fixtures stable.
- `${PIPESTATUS[0]}` in a `verify` block: `$?` after a pipe reports the LAST command. Use
  `set -o pipefail` or `${PIPESTATUS[0]}` **inside a `bash -c '...'` wrapper** — this repo
  has a CI guard that fails on the broken form, and the interactive shell here is zsh
  (where the array is `pipestatus`), so always wrap in `bash -c`.
</gotchas>

<anti_patterns>
- **Do NOT weaken the existing 60 tests to accommodate the new default.** If an existing
  test depends on missing-state-defaults-to-pass, that test **encoded the bug** — change it
  deliberately and say so explicitly in the SUMMARY with the reasoning. (Planning found no
  such test; if one surfaces, this is the rule.)
- Do NOT auto-create a `labels.json` entry for an unlabelled state. Fabricating the label
  is the same lie one layer up.
- Do NOT make an unlabelled state `fail`. It conflates "nothing looked at this" with

- No new dependencies. Node built-ins only.
