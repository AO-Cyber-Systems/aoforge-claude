<embedded_context>

<codebase_examples>
The dogfood helper that will throw once the exit code changes
(`flutter-ui-eval-dogfood.test.cjs:21-26`):

```js
function runRaw(argStr, opts = {}) {
  return execSync(`node ${DF_TOOLS} ${argStr}`, { encoding: 'utf-8', ...opts });
}
function runJSON(argStr) {
  return JSON.parse(runRaw(`${argStr} --raw`));
}
```

`execSync` throws on non-zero exit; the thrown error carries `.stdout` and `.status`. The
minimal deliberate update is a helper that returns `{ stdout, status }` and lets each case
assert both — content assertions untouched.

Planning confirmed there is currently no `process.exitCode` or `process.exit` anywhere in
`flutter-ui-eval.cjs` (nor in `flutter-state-coverage.cjs`).

verifier.md Step 8c captures stdout without `set -e`:
```bash
UI_EVAL=$(node ~/.claude/devflow/bin/df-tools.cjs verify flutter-ui-eval "$OBJECTIVE" --raw)
```
so a non-zero exit yields an empty-or-populated `$UI_EVAL` and does not abort the agent.
</codebase_examples>

<gotchas>
- **Use `process.exitCode = 1`, not `process.exit(1)`.** `process.exit` can truncate
  buffered stdout, and X1 requires the rollup JSON to still be fully readable on a failing
  run. Setting `exitCode` lets Node flush and exit naturally.
- Only `verdict: 'fail'` should exit non-zero. `pass-with-reviews` must exit 0 — a review
  is a request for a human look, not a regression.
- The command is dispatched from `df-tools.cjs`; confirm nothing downstream resets
  `process.exitCode` before the process ends.
- `${PIPESTATUS[0]}` inside `bash -c '...'`; never bare `$?` after a pipe. When asserting
  exit codes in a `verify` block, run the command WITHOUT a pipe and read `$?` directly, or
  wrap explicitly.
</gotchas>

<anti_patterns>
- Do NOT relax any existing content assertion to make the call sites compile. If DF3
  asserted `fails: ['broken-overflow']` before, it asserts it after. Only exit-code handling
  moves.
- Do NOT make the error/not-found path exit non-zero without deciding deliberately — Step 8c
  routes it to `SKIPPED, NEVER a hard fail`. X4 exists to pin whatever you decide.
- Do NOT change `flutter-state-coverage.cjs` here. Out of scope; note it for follow-up.
- No new dependencies.
</anti_patterns>

<error_recovery>
- If the whole dogfood file starts erroring with `Command failed`, that is `execSync`
  throwing, i.e. the expected consequence — update the helper, do not revert the exit code.
- If X1's stdout comes back empty, you used `process.exit()` instead of `process.exitCode`.
</error_recovery>
