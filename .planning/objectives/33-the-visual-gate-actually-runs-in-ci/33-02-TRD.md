<gotchas>
- **`execSync` throws on a non-zero exit.** Objective 32-04 makes a `fail` verdict exit
  non-zero. V2's fixture manifest must therefore be one that scores clean, or V2 must catch
  and read `e.stdout`. Build V2's fixture from the checked-in `good-dashboard` state plus a
  matching `labels.json` so it scores `pass` — otherwise V2 fails for a reason that has
  nothing to do with this TRD.
- **The `absent` and `not_applicable` paths must exit 0.** Step 8c's standing contract is
  "NEVER a hard fail", and 32-04 only makes *judged failures* exit non-zero. If a missing
  manifest starts exiting non-zero, every non-UI objective's verification breaks. V3 pins
  the exit code explicitly.
- **`output()` shape matters.** Emitting `{ status: 'absent', ok: false }` would make Step 8c
  read it as an error and skip — reproducing the bug through a new field name. The
  non-scoring statuses are `ok: true` with a `resolution`; only a genuinely broken
  invocation (no argument at all) stays `ok: false`.
- **Do not change the `--help` output shape** — dogfood Case D1 matches on it.
- **`target.manifest` must exist, and 33-01 Case M8 is what guarantees it.** Everything
  downstream reads `manifest.samples`, `manifest.flakeBudget` and the `manifest.states` loop
  (`flutter-ui-eval.cjs:557-572`). If the resolver validated by calling `loadManifest` and
  DISCARDED the result, `target.manifest` is `undefined` and you get
  `Cannot read properties of undefined (reading 'samples')` — a crash, not a failed
  assertion, landing squarely in V2. Before wiring, confirm the contract holds:
  `node -e "const{resolveUIEvalTarget:r}=require('./flutter-ui-eval-resolve.cjs');console.log(r(process.cwd(),'__fixtures__/flutter-ui-eval/manifest.json').manifest.states.length)"`
  from `bin/lib` must print a number. If it throws, fix 33-01's resolved branch — do NOT
  re-read and re-parse the file here, which would duplicate work the resolver already did
  and re-create the drift this objective closes.
- **Require cycle.** `flutter-ui-eval.cjs` will require `flutter-ui-eval-resolve.cjs`, which
  lazily requires `loadManifest` back from `flutter-ui-eval.cjs`. 33-01 was told to keep that
  require **inside the function** for exactly this reason. If you see `loadManifest is not a
  function` at runtime, a top-level require crept in — move it back inside.
- **`path` argument still means path.** Tier 1 of the resolver is "the argument names an
  existing file". Do not add a heuristic that inspects the string for digits or extensions;
  `verify flutter-ui-eval 33` and `verify flutter-ui-eval ./33.json` must both do the
  obvious thing, and existence on disk is what separates them.
- `${PIPESTATUS[0]}` in a `verify` block: `$?` after a pipe reports the LAST command. Use
  `set -o pipefail` or `${PIPESTATUS[0]}` **inside a `bash -c '...'` wrapper** — this repo
  has a CI guard that fails on the broken form, and the interactive shell here is zsh (where
  the array is `pipestatus`), so always wrap in `bash -c`.
</gotchas>
