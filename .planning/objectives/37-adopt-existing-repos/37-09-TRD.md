# TRD 37-09: `/devflow:adopt` skill and workflow; map-codebase non-interactive; new-project hooks

<objective>
Write the LLM half. The skill is a thin orchestrator; the workflow calls the deterministic
subcommands in order and does only what needs judgement: mapping the code and inferring
PROJECT.md. It never asks — uncertainty is written down with its confidence and evidence for
ADOPT-REPORT.md. map-codebase gains a non-interactive mode for it, and new-project learns to point
at adopt and to register the repo with the pruner.

`type: standard`: the markdown is not unit-testable behaviour, but its contract is — Task 3's
static contract test is written test-first (`tdd="true"`).

Resolved intent: kind=plugin, work=feature, tdd=strict, test_list_first=required.
Constraints honored: `no_llm_test_data`, `no_property_based_default`, `no_gherkin_layer`.
</objective>

## Runtime model (binding, from OBJECTIVE.md)

- Markdown files follow the repo conventions: YAML frontmatter + XML-like `<step name="...">`
  sections; `@~/.claude/devflow/...` references (never `${CLAUDE_PLUGIN_ROOT}` in `@path`).
- The contract test is CommonJS, synchronous fs, no new dependencies; it reads files only.
- The workflow text must itself encode the runtime rules for whoever runs it: one plain command per
  Bash call, commits only through df-tools commit, never bypass signing, never push, never port
  8080.
- Commits via `node ~/.claude/devflow/bin/df-tools.cjs commit "<msg>" --files <paths>`; signing
  failure → STOP and report. No version bump, tag or push.
- Commits: `test(37-09): ...` → `feat(37-09): ...` / `docs(37-09): ...`.

adopt.md steps (each a `<step name="...">`; DF = `node ~/.claude/devflow/bin/df-tools.cjs --cwd "$TARGET"`,
written out in full on every line, not as a shell variable, so each Bash call is one plain command):

   not exist → say so, stop.
2. `preflight` — `DF adopt preflight`. Parse JSON; handle routes as in must_haves. For `resume`, note

3. `begin` — `DF adopt begin` (idempotent), then `DF skill-active --start adopt`.

5. `infer_project` — unless `steps.project_md`: read the 8 maps, README*, the manifests; write
   `$TARGET/.planning/PROJECT.md` (frontmatter `kind`, `default_work`; the sections in test 9;
   Validated = what the code already does, each with a file path; Active = "None yet — add with
   /devflow:objective add"; Out of Scope empty; Constraints from STACK/CONCERNS maps) and
   `$TARGET/.planning/.adopt-inferences.json` (array of {field, value, confidence, evidence}; one
   entry each for kind, default_work, core_value, every Validated item, every Constraint).
   Rubric: api = network server entrypoint (net/http ListenAndServe, express/fastify listen, gRPC
   server); app = end-user application (Flutter `runApp`, web/mobile UI entry); library = importable
   package, no entrypoint; ui-lib = component library (widgets/components exported, no app entry);
   cli = declared binary / arg-parsing main without a server (package.json `bin`, cobra/flag, clap);
   plugin = extends a host (Claude Code plugin manifest, editor/extension manifest).
   default_work: `feature` with `medium` confidence unless the repo states otherwise.
6. `scaffold` — `DF adopt scaffold`. Exit 1 with a PROJECT.md problem → fix that field once and
   retry; still failing → stop with the resume hint (re-run `/devflow:adopt`).
7. `health` — `DF validate health --raw`; errors > 0 → `DF validate health --repair` once and re-check;
   still errors → run step 8 (so the report lists them), skip step 9, stop with the resume hint.
8. `report` — `DF adopt report`; keep `commit_files` and `commit_message`.
9. `commit` — `DF skill-active --end`, then `DF commit "<commit_message>" --files <commit_files...>`.

10. `summary` — branch `devflow/adopt`, commit sha (`git -C "$TARGET" rev-parse --short HEAD`),
