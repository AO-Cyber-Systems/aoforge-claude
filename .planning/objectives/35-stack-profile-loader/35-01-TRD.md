# TRD 35-01: Extract the schema walker into `json-schema-lite.cjs` and teach it the stack-profile keywords

<objective>
Move the hand-rolled JSON-Schema walker out of `lib/ui-spec-validate.cjs` into a shared
`lib/json-schema-lite.cjs`, and add the keywords `schemas/stack-profile.schema.json` relies on:
`propertyNames`, `minLength`, `uniqueItems`, `const`, union `type: [...]`, `format: date`, and
object-form `additionalProperties`. Today `typeOk` returns `true` for an array `type`, so a union
type passes anything — that is a latent bug this TRD fixes for the new caller only (surface-spec
schema uses no union types).

Gate: the ui-spec suites stay green and unchanged.

Resolved intent: kind=plugin, work=feature, tdd=strict (OBJECTIVE `overrides.tdd`),
depth=comprehensive, test_list_first=required, fixture_strategy=generators.
Constraints honored: `no_llm_test_data` (inline hand-written schemas/values), `no_property_based_default`,
`no_gherkin_layer`.
</objective>

## Test list

Write these as `test(...)` cases in `json-schema-lite.test.cjs` (copy this list into the file's
header comment first, house style — see `brownfield-detector.test.cjs:1-27`).

Parity (behaviour extracted from ui-spec-validate.cjs, message text must match exactly):
1. `$ref` chain (`#/$defs/a` → `#/$defs/b`) resolves; a ref to a missing node resolves to `{}` (accepts anything).
2. Type mismatch → exactly one error `expected type string here, got number`; no descent into children.
3. `enum` miss → `value "x" is not one of the declared values: a, b`.
4. `pattern` miss → `"X" does not match the pattern the schema declares here: ^[a-z]+$`.
5. `minimum` → `value 0 is below the declared minimum 1`.
6. `required` key absent → path `obj.key`, message `required key "key" is absent — the schema declares it here`.
7. `additionalProperties: false` unknown key → `unknown key "zz" — the schema declares no such property here`.
8. `items` → element paths `list[1]`.
9. `anyOf`/`oneOf` with no matching branch → `value does not match any form the schema declares for this node (got number)`.

New keywords:
10. Union `type: ["string","null"]`: accepts `null` and `"a"`, rejects `3` with `expected type string|null here, got number`.
11. `const: 1`: accepts `1`, rejects `2` → `value 2 is not the declared constant 1`.
12. `propertyNames: {pattern: "^[a-z][a-z0-9_]*$"}`: key `Bad-Key` → one error at path `obj.Bad-Key`, message starts `property name "Bad-Key":`.
13. `minLength: 1`: `""` rejected → `string is shorter than the declared minLength 1`.
14. `uniqueItems: true`: `["a","a"]` rejected → `array items are not unique: duplicate "a"`; `["a","b"]` passes.
15. `format: "date"`: `"2026-09-27"` passes; `"2026-13-01"`, `"2026-02-30"`, `"yesterday"` fail → `"yesterday" is not a valid date (YYYY-MM-DD)`; a non-string is not format-checked.
16. `additionalProperties: {$ref: "#/$defs/command"}`: an extra key whose value violates the referenced schema yields errors at `commands.test.run`; a conforming one yields none.
17. `minItems: 1` with `[]` → NO error (documents the deliberate non-support; see gotchas).

Positive control (integration):
18. Frontmatter of `plugins/devflow/devflow/references/stack-general.md` and of
    `docs/stack-profiles/go.md`, `dart.md`, `flutter.md` (split on the `---` fences, parsed with
    `parseYamlLite`) validates against `plugins/devflow/devflow/schemas/stack-profile.schema.json`
    with `[]`.
19. A copy of the go profile with `commands.test.run = ""` and `provenance.reviewed = "soon"`
    yields exactly two errors (minLength, format) — proves the positive control is not vacuous.

<gotchas>
- **Order of checks matters for parity.** Keep the old order: anyOf/oneOf → type (return early)
  → enum (return early) → pattern (return early) → minimum → items (return) → object walk. Insert
  new checks where they don't change old outcomes: `const` after enum; `minLength` and `format`
  after pattern (strings only); `uniqueItems` before the `items` walk; `propertyNames` and object-form
  `additionalProperties` inside the object walk.
- **Do not enforce `minItems`.** `surface-spec.schema.json` declares `minItems: 1`; enforcing it
  would add SPEC001 errors the ui-spec suites don't expect. Test 17 pins this.
- **Union type message:** join with `|` (`string|null`).
- **`format: date` validity:** regex `^\d{4}-\d{2}-\d{2}$` AND a real calendar date (construct
  `new Date(Date.UTC(y, m-1, d))` and compare parts back).
- `docs/` is not in the `~/.claude/devflow` mirror. Test 18 reads docs from the checkout via a
  path relative to `__dirname` (`../../../../../docs/stack-profiles`) — that's fine for tests.
- If a shipped profile fails test 18, decide whether the profile or the schema is wrong. Fix the
  **profile** only if it genuinely violates the schema's stated intent; record it as a deviation
  in SUMMARY. Do not loosen the schema to make it pass.
</gotchas>

<anti_patterns>
- Adding an npm JSON-Schema validator (ajv etc.). Forbidden — no new dependencies.
- Rewording existing messages "while you're there". ui-spec tests match on them.
- Duplicating the walker instead of moving it (ui-spec-validate.cjs must not keep its own copy).
</anti_patterns>

`.planning/objectives/35-stack-profile-loader/baseline-failures.tsv`, not counts. That file
has one line per failure: `file:line<TAB>name`, from a real run of this exact command.

   `node --test --test-reporter=spec 'plugins/devflow/**/!(micro).test.cjs' 'plugins/devflow/**/*.test.js' 'scripts/**/*.test.cjs'`
   and write its output to a file in your session scratchpad (never the repo).
2. Extract the failing test names from the spec reporter's closing `✖ failing tests:` section.
   Each entry gives `test at <file>:<line>:<col>` and then `✖ <name> (<ms>)`; strip the duration.
3. A failure whose name appears in the TSV's second column is **pre-existing**, whether it passes
   or fails in your run.
4. A failure whose name is **not** in the TSV is a candidate regression:
   - Re-run just its file with `node --test <file>`.
   - If it passes on re-run, record it as an environment flake with the evidence.
   - If it still fails, check whether this TRD's changes (`git diff --stat` against your wave base)
     touched code that test exercises.
     - If they did, it is a **regression and blocks**. Fix it before completing.
     - If they plainly didn't (e.g. a PTY or handoff timing test), record it in SUMMARY as an
       **environment flake**, with the file, the name, the re-run output and why it's unrelated.
       Don't block.
5. **Never edit `baseline-failures.tsv`** to make the gate pass.

In SUMMARY, record the observed pass/fail totals (for information only) and every failure with its
classification: pre-existing, environment flake, or regression.
