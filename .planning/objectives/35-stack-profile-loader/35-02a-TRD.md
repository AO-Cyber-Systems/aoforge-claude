# TRD 35-02a: The stack-profile loader core — parse and resolve

<objective>
Add `lib/stack-profile.cjs`, modelled on `lib/defaults-loader.cjs`, which parses stack profiles
and resolves the tier chain with provenance. Command rendering and per-agent slicing are
35-02b (a separate module, `lib/stack-render.cjs`, built in parallel); 35-03 re-exports them.
No CLI here (35-03), no validation codes (35-03), no drafting (35-04).
Split from the original 35-02 at the job-checker's request (41 cases was too many for one executor).

Resolved intent: kind=plugin, work=feature, tdd=strict, depth=comprehensive,
test_list_first=required, fixture_strategy=generators → Task 1 builds the fixture factories first.
Constraints honored: `no_llm_test_data` (hand-built profile strings), `no_property_based_default`,
`no_gherkin_layer`.
</objective>

## Runtime model (binding, from OBJECTIVE.md)

- Skills/agents run the MIRROR `~/.claude/devflow/bin/df-tools.cjs`; tests `require()` from the checkout.
- CommonJS, synchronous fs, **no new npm dependencies**. Parse with `yaml-lite.cjs`, **not**
  `frontmatter.cjs` (it returns flow maps like `{ run: discover }` as strings).
- **Org tier only when `userHome` is passed.** Tests pass an `mkdtemp` fake home. **Never read the
  real `~/.claude` in a test.**
- `~/.claude/devflow/stacks/` is outside sync-runtime's SUBDIRS (`workflows references templates bin schemas`) — it is never overwritten by the mirror.
- **Neutrality:** stack-profile.cjs names no specific stack.
- One plain command per Bash call. 1Password signing failure → STOP and report; never `commit.gpgsign=false`.

## Contract (other TRDs depend on this exact shape)

```js
parseProfile(text, { source }) → {
  frontmatter,                 // parsed YAML object ({} if the block is empty)
  sections: [{ name, text, inherit }],   // H2 sections in file order; text excludes the heading and the inherit marker, trimmed
  bodyLineCount,               // lines after the closing fence (for 35-03's >150 warning)
}
// throws StackProfileError{code:'NO_FRONTMATTER'|'UNTERMINATED'|'NOT_A_MAPPING'|'YAML', source}

resolveProfile({ projectRoot = null, userHome = null, file = null } = {}) → {
  id,                          // highest tier's id ('general' when no STACK.md)
  frontmatter,                 // merged
  sections: { [name]: { text, sources: [tier...] } },
  provenance: { 'commands.test': 'bundled'|'org'|'project'|'component', 'loop': ..., 'gates.task': ..., 'id': ..., ... },
  chain: [{ id, tier, path }], // low → high: general first
  component: null | { path, profile },
  issues: [{ code, message, id? }],   // EXTENDS_UNRESOLVED | EXTENDS_CYCLE | EXTENDS_DEPTH | COMPONENT_MISSING
  projectFile: null | '<abs path to .planning/STACK.md>',
}
// throws StackProfileError only when a file in the chain cannot be parsed (message names the file)

SECTION_NAMES = ['Principles','Idioms','Avoid','Layout & architecture','Testing','Dependencies','Generated code','Security','UI']
```

Provenance leaves: recurse into plain-object maps; stop at arrays, scalars, and at each
`commands.<key>` (atomic). Tier names: `bundled` (general), `org` (any stacks/<id>.md in the
chain), `project` (.planning/STACK.md), `component`.

## Test list

Copy into the header comment of `stack-profile.test.cjs` before writing tests.

Parse (Task 1):
- P1 well-formed text → `{frontmatter, sections, bodyLineCount}`; section names in order.
- P2 BOM + CRLF input parses identically to LF input.
- P3 no opening `---` → `StackProfileError` code `NO_FRONTMATTER`.
- P4 unterminated block → code `UNTERMINATED`.
- P5 a `---` horizontal rule in the body does not split anything.
- P6 `extends: null` → `null`; `test: { run: discover }` → object `{run:'discover'}` (proves yaml-lite).
- P7 H1 and prose before the first H2 are not a section.
- P8 a `## Heading` line inside a ``` fence is not a split.
- P9 `<!-- inherit -->` as the first non-blank line → `inherit:true`, marker removed from `text`.
- P10 positive control: `references/stack-general.md` and `docs/stack-profiles/{go,dart,flutter}.md` parse; flutter has exactly two `inherit:true` sections; general has sections Principles, Avoid, Testing, Dependencies.

Resolve (Task 2):
- R1 no STACK.md → id `general`, chain length 1, every provenance value `bundled`, `issues: []`.
- R2 STACK.md without `extends` overriding `commands.test` → provenance `commands.test: project`, `commands.build: bundled`.
- R3 `extends: golike` + fake home with `stacks/golike.md` → chain general→golike→project; `commands.test.scoped` comes from org; provenance `org`.
- R4 project `commands.test: { run: "x" }` over an org test with `scoped` → merged test is exactly `{run:'x'}`.
- R5 lists replace: project `loop: [test]` → `['test']`.
- R6 maps deep-merge: project `generated.globs` + bundled `generated.markers` both present; provenance per leaf.
- R7 two-hop org chain (a extends b extends general) resolves in order general, b, a, project.
- R8 cycle a↔b → one `EXTENDS_CYCLE` issue; no throw; chain ends at general.
- R9 chain of 5 org hops → `EXTENDS_DEPTH`.
- R10 `extends: nope` with a fake home lacking it → `EXTENDS_UNRESOLVED`; frontmatter as if extends general.
- R11 `userHome: null` + `extends: golike` → `EXTENDS_UNRESOLVED` even though a fake home with golike exists elsewhere (never guessed).
- R12 project `## Avoid` replaces general's; project `## Testing` with inherit → general text then project text; `sources` lists both tiers.
- R13 project `## Principles` (no marker) → general's Principles first, project text appended.
- R14 components `[{path:'apps/',...},{path:'apps/web/',...}]`, `file:'apps/web/x.ts'` → component `apps/web/`, its overrides have provenance `component`; `file:'lib/y.ts'` → `component: null`.
- R15 component `profile: golike` (an org id, not a path) resolves through the org dir.
- R16 cache: same args → same object (`===`); `_resetCache()` → fresh object; different `userHome` → different entry.
- R17 malformed STACK.md → throws `StackProfileError` whose message contains the file path.

Neutrality (Task 2):
- P11 the source of stack-profile.cjs does not match `/golang|gofmt|\bdart\b|flutter|pubspec|\bnpm\b|cargo|pytest|rails|gradle|swift|kotlin/i`.

<gotchas>
- **Component merge rule (locked here):** the component tier merges on top of the full project
  resolution. If `profile` ends with `.md` it's a path relative to projectRoot; otherwise it's an
  org id, whose own chain (minus general and minus anything already in the project chain) merges
  on top with tier `component`. Missing component file → `COMPONENT_MISSING` issue, resolution continues.
- **Depth:** count org hops only (the project file and general don't count). 4 hops OK, 5 → `EXTENDS_DEPTH`.
- **Cycle detection:** keep a `seen` Set of ids while walking `extends`; revisiting → issue, stop walking.
- yaml-lite rejects a trailing comment on a block-opening key (`commands:   # x`) — put comments on their own line in fixtures.
- Quote `"off"` and dates in fixture YAML.
- `_resetCache()` in `beforeEach` of every test group that rewrites a fixture file.
</gotchas>

<anti_patterns>
- Using `frontmatter.cjs` — returns flow maps as strings.
- Reading `os.homedir()` anywhere in this module. The CLI (35-03) passes it; the lib never guesses.
- Naming any stack in lib code or comments (P11 enforces).
- Throwing on extends problems — they are `issues`, so validate/health can report them.
</anti_patterns>

## Regression gate (baseline-relative)

Test counts depend on the environment. The 1Password signing hang only happens where
`op-ssh-sign` is reachable: a sandbox saw 3417 pass / 1 fail, while the user's machine sees 10
failures. So this gate compares failing test **names** against
`.planning/objectives/35-stack-profile-loader/baseline-failures.tsv`, not counts. That file
has one line per failure: `file:line<TAB>name`, from a real run of this exact command.

1. From the repo root, run
   `node --test --test-reporter=spec 'plugins/devflow/**/!(micro).test.cjs' 'plugins/devflow/**/*.test.js' 'scripts/**/*.test.cjs'`
   and write its output to a file in your session scratchpad (never the repo).
2. Extract the failing test names from the spec reporter's closing `✖ failing tests:` section.
   Each entry gives `test at <file>:<line>:<col>` and then `✖ <name> (<ms>)`; strip the duration.
3. A failure whose name appears in the TSV's second column is **pre-existing**, whether it passes
   or fails in your run.
4. A failure whose name is **not** in the TSV is a candidate regression:
   - Re-run just its file with `node --test <file>`.
   - If it passes on re-run, record it as an environment flake with the evidence.
   - If it still fails, check whether this TRD's changes (`git diff --stat` against your wave base)
     touched code that test exercises.
     - If they did, it is a **regression and blocks**. Fix it before completing.
     - If they plainly didn't (e.g. a PTY or handoff timing test), record it in SUMMARY as an
       **environment flake**, with the file, the name, the re-run output and why it's unrelated.
       Don't block.
5. **Never edit `baseline-failures.tsv`** to make the gate pass.

In SUMMARY, record the observed pass/fail totals (for information only) and every failure with its
classification: pre-existing, environment flake, or regression.
