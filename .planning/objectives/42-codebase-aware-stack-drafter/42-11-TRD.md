# TRD 42-11: Fleet rollout — verified STACK.md + STACK-REPORT.md across ~/dev

<objective>
SDR-08 / ROADMAP criterion 6. Run the new drafter against every canonical DevFlow repo in
`/Users/justin/dev`. It is operational and checkpointed:
1. Dry-run everything read-only, and write a review table to `42-ROLLOUT.md`.
2. STOP for human review (checkpoint:human-verify).
3. For each approved, eligible repo: `stack init --write`, `stack verify --run` (safe keys only),
   `stack report --write`, then `df-tools commit --files .planning/STACK.md .planning/STACK-REPORT.md`
   on the repo's CURRENT branch.
4. Record results in `42-ROLLOUT.md`.

Locked: never push. Never write `.mcp.json` (Q4). Commit only those two files. Skip worktrees. Nested
`.planning` dirs are components of their parent.

## Binding rules

- Run df-tools from THIS checkout, not the stale mirror: `DF=<your working checkout>/plugins/devflow/devflow/bin/df-tools.cjs`.
  Invoke it as `node $DF --cwd /Users/justin/dev/<repo> ...`. If you run in a worktree, `DF` is that
  worktree's path. The code is identical at the wave base.
- One plain command per Bash call. Loop in a small Node script under the session scratchpad (not
  committed) when iterating ~35 repos. The script may run the read-only dry run. Every WRITE step runs
  only after the checkpoint.
- NEVER: `git push`, tags, releases, version bumps, `stack mcp --write`, `stack init --force` (unless
  the human explicitly approves force for a named repo at the checkpoint), deploys, or anything on port 8080.
- Never commit with raw git in other repos. Use `node $DF --cwd <repo> commit "<msg>" --files .planning/STACK.md .planning/STACK-REPORT.md`.
- Do not modify, stash, reset or checkout anything else in another repo. Dirty trees stay as they are.

<anti_patterns>
- Treating a `.git` FILE dir as a repo. That's a worktree, so skip it.
- Descending into nested `.planning` (opsCluster/control-plane, aoCyberSecurity/*, aocore-wave-*/N).
- Overwriting an existing STACK.md. List it as `has-stack` and report its validation. The human
  decides at the checkpoint (report-only, force, or skip).
- Running `stack verify --run --include test` by default. Tests may need Postgres or ports. Only with
  explicit per-repo approval.
- Committing a repo whose `stack verify --run` showed exit 126/127 or spawn errors. That's a wrong
  command, not a red gate.
</anti_patterns>

<error_recovery>
- `stack init --write` leaves `action: preview` (the draft failed validation): mark the repo blocked
  `draft-invalid`, capture `validation.errors`, write nothing, and move on.
- The commit returns `committed:false`: record the reason verbatim as blocked. Leave the written
  files in place and list them. Don't retry with raw git.
- Anything unexpected in another repo (e.g. `git status` shows files other than the two new ones
  changed by our run): STOP the loop and surface it. Don't attempt cleanup beyond deleting the two
  files we created in that repo, and only if they're uncommitted.
</error_recovery>
