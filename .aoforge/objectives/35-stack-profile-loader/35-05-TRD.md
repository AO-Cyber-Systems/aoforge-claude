## Code mapping (locked)

| Health code | Severity | From STK codes | Message | Fix |
|---|---|---|---|---|
| E030 | error | STK001, STK003, STK004, STK006, STK008, STK009 | `stack-profile-invalid: .planning/STACK.md — <first error code>: <msg> (+N more)` | `Run \`df-tools stack validate\` for the full list and fix .planning/STACK.md` |
| W030 | warning | STK002 | `stack-extends-unresolved: extends "<id>" not found in ~/.claude/devflow/stacks/` | `Install ~/.claude/devflow/stacks/<id>.md or change \`extends\`` |
| W031 | warning | STK005 | `stack-undefined-command: <field> names "<key>", which no tier defines` | `Define commands.<key> in .planning/STACK.md or remove it from <field>` |
| W032 | warning | validator warnings (STK007) | `stack-profile-warning: <msg>` | `Trim the profile body; link to skills/docs instead of pasting them` |
| I030 | info | STACK.md absent AND `detectManifest(cwd, {userHome: homeDir}).has_manifest` | `stack-profile-absent: a <primary_lang> manifest is present but .planning/STACK.md is not (general profile in use)` | `Draft one with \`df-tools stack init\`, review it, then \`df-tools stack init --write\`` |

One E030 per run (aggregate), one W030/W031 per distinct issue. `repairable` is always `false`.
If `validateProfile` itself throws (e.g. bundled general missing), add E030 with the error message — a check that could not run is never silent.

## Regression gate (baseline-relative)

Test counts depend on the environment. The 1Password signing hang only happens where
`op-ssh-sign` is reachable: a sandbox saw 3417 pass / 1 fail, while the user's machine sees 10
failures. So this gate compares failing test **names** against
`.planning/objectives/35-stack-profile-loader/baseline-failures.tsv`, not counts. That file
has one line per failure: `file:line<TAB>name`, from a real run of this exact command.

1. From the repo root, run
   `node --test --test-reporter=spec 'plugins/devflow/**/!(micro).test.cjs' 'plugins/devflow/**/*.test.js' 'scripts/**/*.test.cjs'`
   and write its output to a file in your session scratchpad (never the repo).
2. Extract the failing test names from the spec reporter's closing `✖ failing tests:` section.
   Each entry gives `test at <file>:<line>:<col>` and then `✖ <name> (<ms>)`; strip the duration.
3. A failure whose name appears in the TSV's second column is **pre-existing**, whether it passes
   or fails in your run.
4. A failure whose name is **not** in the TSV is a candidate regression:
   - Re-run just its file with `node --test <file>`.
   - If it passes on re-run, record it as an environment flake with the evidence.
   - If it still fails, check whether this TRD's changes (`git diff --stat` against your wave base)
     touched code that test exercises.
     - If they did, it is a **regression and blocks**. Fix it before completing.
     - If they plainly didn't (e.g. a PTY or handoff timing test), record it in SUMMARY as an
       **environment flake**, with the file, the name, the re-run output and why it's unrelated.
       Don't block.
5. **Never edit `baseline-failures.tsv`** to make the gate pass.

In SUMMARY, record the observed pass/fail totals (for information only) and every failure with its
classification: pre-existing, environment flake, or regression.
