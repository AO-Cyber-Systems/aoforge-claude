# TRD 42-06: Command verification — `stack verify [--run]`

<objective>
SDR-03, plus locked decision Q7: `stack verify [--run]` lives in the CLI. Build `stack-verify.cjs`:
- A deterministic, injectable resolvability check. Is the binary on PATH? Does the make/task/just target exist? Does the script exist?
- An opt-in executor (`--run`) that runs only safe gate keys, with a strict deny policy.

The drafter (42-07) uses `verifyCommand` to decide between proposing a command and writing
`run: discover`. The fleet rollout (42-11) uses `stack verify --draft` in the dry run, and
`stack verify --run` after approval.

Locked decision Q2: target_missing, script_missing and binary_missing ALL mean "not proposed". This
module only reports status. The drafter applies the policy.

Output: stack-verify.cjs, its test, and a fixture module.
</objective>

## Test list

Outermost (CLI) to innermost (resolver).

1. CLI `stack verify --raw` on a fixture repo with STACK.md (test: `make test`, lint: `golint-x ./...`, format: `./scripts/fmt-check.sh`) and a fake PATH gives JSON results: test resolved, lint binary_missing, format script_missing. Exit code is 1 when any status isn't resolved. No file is written (snapshot of dir mtimes).
2. CLI `stack verify --draft --raw` on a repo without STACK.md verifies the initProfile preview's commands, and `.planning/STACK.md` still doesn't exist afterwards.
3. CLI `stack verify --run --raw` with stub binaries: format and lint run with exit 0; `test` is skipped with reason `not-included`; `--include test` runs it. A failing stub (`exit 3`) gives `run.exit_code: 3` and CLI exit 1.
4. Components: a STACK.md with `components: [{path: "svc/", profile: <inline file>}]` yields results tagged `component: 'svc/'`. `cwd` equals exactly what `renderCommand` returned for that component view. Before 42-05 that is `undefined` for a command without its own cwd; 42-05 changes the expectation to `'svc'`. Add an explicit assertion that cwd is never `svc/svc`.
5b. Deny policy on expanded bodies, table-driven (one level via `readRunners`):
   - `make build` whose Makefile `build:` body runs `docker push registry/x:tag` is refused, reason `body:docker-push`
   - `task ship` whose cmds include `kubectl apply -f k8s/` is refused
   - `just release` whose body runs `gh release create v1` is refused
   - `npm run build` whose script is `tsc && npm publish` is refused
   - `pnpm run lint` whose script is `eslint . && git push` is refused
   - `make lint` whose body is `golangci-lint run` runs
   - `make build` whose body calls another target (`\t$(MAKE) push`) is refused as `unverifiable-body` (the one-level limit; the nested target isn't expanded)
   - direct gate `./scripts/release.sh` whose file runs `git push origin main` is refused, reason `body:git-push`
   - `bash scripts/ci.sh` / `sh scripts/ci.sh` whose file runs `docker push x` are refused
   - `make deploy-check` whose Makefile target line calls `./scripts/deploy.sh`, where deploy.sh runs `kubectl apply -f k8s/`, is refused (a wrapper inside a runner body is expanded)
   - `bin/check` (an executable without `.sh`) whose body runs `npm publish` is refused
   - `./scripts/lint.sh` whose file is only `golangci-lint run ./...` runs
   - `./scripts/missing.sh` (absent or unreadable) is refused as `unverifiable-body`
   - `./scripts/outer.sh` whose file calls `./scripts/inner.sh` or `make push` is refused as `unverifiable-body` (a wrapper that invokes another script or runner target isn't expanded further)
   The spawn spy count is 0 for every refused row.
5. Deny policy, table-driven. Each is refused with a named reason and never spawned (spy): `make deploy`, `npm publish`, `dart pub publish`, `gh release create`, `goreleaser release`, `docker push x`, `docker buildx build --push .`, `kubectl apply -f k8s/`, `helm upgrade --install x`, `terraform apply`, `npm run dev`, `flutter run`, `go run ./cmd/server --port 8080`, `task release:tag`. `docker build .` is skipped with reason `container-build`.
6. Key policy: `codegen`, `deps`, `tidy.apply`, `format.apply`, `fix.apply` are never run.
7. `verifyCommand('make -C svc test')` with target present gives resolved. Absent gives target_missing. With `include` and absent gives unverifiable.
8. `task lint:go`, `just test` and `pnpm run build` are checked against their runner files. The runner binary also has to be on the fake PATH, else binary_missing.
9. `./bin/test.sh` present and executable gives resolved. Present but not executable gives script_missing with detail `not executable`. `bash scripts/x.sh` needs only existence.
10. `HOME=/root ginkgo -r -p` with ginkgo absent gives binary_missing (the env prefix is stripped). `cd svc && go vet ./...` checks `go`.
11. `npx playwright test` with no `node_modules/.bin/playwright` and no dependency gives unverifiable (low).
12. `go run ./cmd/tool` with the dir present gives resolved. Absent gives script_missing.
13. `resolveBinary('gopls', { PATH: fakeBin, home: fakeHome })` finds `fakeHome/go/bin/gopls` when it is not on PATH.

Only the `run` form is ever executed. Deny regexes cover the Test-list case 5 table, `git push`, and
`/\b8080\b/` → `port-8080-forbidden`.
Body expansion, before any spawn: normalise the command with `stack-shell.normalizeScript`. For every
invocation that is a make/task/just target or an npm/pnpm/yarn/bun script, look the target up with
`stack-runners.readRunners(root)` (cached per root) and run the SAME deny/skip regexes over each body
line. A hit refuses the whole command with reason `body:<deny-reason>` and `detail: '<runner> <target>: <line>'`.
Shell wrapper scripts are body-expansion cases too. That covers an invocation of `./x.sh`,
`bash x.sh`, `sh x.sh` or `bin/x`, whether it is the gate command itself or a line inside a runner
target or npm-script body. Read the file (via `readRunners`' script entries when present, else `fs`,
resolved against the invocation's cwd) and apply the same deny/skip regexes to every non-comment line.
An unreadable or missing file means `unverifiable-body`.
Expansion is one level deep. A runner body is scanned, and a wrapper script referenced from that body
is scanned too. If any scanned body or script invokes another runner target (`$(MAKE) push`,
`task other`, `npm run x`) or another script (`./y.sh`, `bash y.sh`), that nested item is NOT expanded,
and the command is refused as `unverifiable-body`.
Known consequence: repos whose Makefiles use `include` or recursive `$(MAKE)` will have those gates
refused as `unverifiable-body` in `--run` (safe by default). The result carries
`skipped: 'unverifiable-body'` so 42-11 can count them. A target not found statically
(e.g. an include-expanded Makefile) is refused as `unverifiable-body`, since we can't prove it's safe. Each result gets
`run: { exit_code, duration_ms, timed_out, tail }` or `run: { skipped: reason }`.
