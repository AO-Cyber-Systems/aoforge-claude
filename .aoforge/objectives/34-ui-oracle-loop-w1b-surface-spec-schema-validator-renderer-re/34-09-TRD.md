# TRD 34-09: the agent shell harness — extraction, the call model, and cwd that persists

<objective>
Build the executable check that proposal §21 amendment 1 makes binding: a harness that runs the
fenced bash from a named agent-prose section **under the real Bash-tool model** — cwd persists
between calls, environment does not, one command per call — and asserts what each call did.

This TRD builds and unit-tests the harness in isolation against hand-written markdown. **It
points at no real agent file.** 34-10 aims it at `agents/executor.md`, adds the scratch monorepo
and the CI job.

Resolved intent: kind=plugin, work=feature, tdd=strict, depth=comprehensive,
test_list_first=required, fixture_strategy=generators. Constraints honored:
`no_llm_test_data` (every markdown input is hand-written in the test file),
`no_property_based_default`, `no_gherkin_layer`.
</objective>

## Runtime model

Binding for this TRD (OBJECTIVE.md; proposal §21 amendment 2) — and, unusually, it is also the
SUBJECT of this TRD. The harness's job is to make the second bullet executable.

- **Mirror, not checkout.** Skills invoke `node ~/.claude/devflow/bin/df-tools.cjs` — the MIRROR
  at `~/.claude/devflow`, copied from `plugins/devflow/devflow/` by `sync-runtime`. It is NOT
  this checkout. `installed_plugins.json` is registry truth; `pluginVersion()` is the running
  engine. Tests invoke the LOCAL binary by absolute path.
- **Bash tool semantics — the model this harness reproduces.** The working directory PERSISTS
  across Bash calls. Shell variables, functions and exported environment do NOT. The worktree
  guard refuses compound commands it cannot statically verify, so agents emit ONE plain command
  per call. Package-relative work therefore goes in a `( cd "$DIR" && … )` subshell — a bare
  `cd X && cmd` leaks the working directory into every subsequent call. Evidence paths are
  absolute from a per-call `REPO_ROOT`, re-derived in the call that uses it.
- **CommonJS only.** `.cjs`, synchronous `fs`, adjacent tests. **No new npm dependencies** —
  `node:child_process` `execFileSync` is the executor.
- **Honest output.** A section the harness could not execute reports `MISSING` with the reason.
  Never `pass`.

<test_list>
Behaviour cases, written before any test code. Outside-in: extraction guards FIRST (a harness
that finds nothing and reports green is worse than no harness), then splitting, then the runtime

**Extraction (E) — the guards, written first**
- **E1** — a named section that does not exist in the markdown -> ERROR naming the section.
  Never `{ok: true, calls: []}`. This is `verifier-ui-eval-invocation.test.cjs`'s V4 lesson:
  *a regex that matches zero times and an assertion that iterates zero times is a green test
  proving nothing.*
- **E2** — a section that exists but contains zero fenced ```bash blocks -> `MISSING` with the
  reason, not `pass`.
- **E3** — extraction is bounded by the NEXT heading at the same or higher level. A ```bash block
  in the following section is not collected. Assert with a fixture containing two sections, each
  with a distinguishable block.
- **E4** — non-bash fences (```yaml, ```markdown, ```) inside the section are ignored, and a
  fence with an info string of `bash` plus attributes (```bash title=x) IS collected.

**Call splitting (S)**
- **S1** — a block of three single-line commands -> three calls, in order, each with its 1-based
  source line.
- **S2** — a line ending in `\` continues onto the next line: ONE call. The executor's real
  `flutter drive` block spans four lines this way; splitting it would produce three broken calls.
- **S3** — full-line comments become ANNOTATIONS attached to the NEXT call, not calls of their
  own. Trailing comments stay on their call. (34-10's `# harness:` vocabulary is built on this.)
- **S4** — blank lines are separators, not calls. A heredoc (`<<'EOF' … EOF`) is ONE call — pin
  it even though the executor's current blocks have none, because the gate-commits hook's
  heredoc handling shows this repo writes them.

**The runtime model (X) — the point of the TRD**
- **X1 (the plan's first RED case)** — a section whose block is
  `cd sub` / `touch marker.txt`: the harness detects that call 1 changed the persisted cwd and
  **FAILS the section**, with a finding naming the call, `cwd_before` and `cwd_after`. Assert
  `ok === false` and that the finding's text contains both paths.
- **X2 (the plan's second RED case)** — `( cd sub && touch marker.txt )`: cwd is unchanged after
  the call, the section PASSES, and `sub/marker.txt` exists.
- **X3 (the plan's third RED case)** — call 1 is `REPO_ROOT=$(pwd)`, call 2 is
  `echo "$REPO_ROOT"`: call 2 FAILS with an unset-variable diagnosis. The harness runs each call
  with `set -u` and a FRESH env, so the failure is real rather than simulated. Assert the finding
  names the variable.
- **X4** — the same two calls where call 2 RE-DERIVES (`REPO_ROOT=$(pwd); echo "$REPO_ROOT"` in
  one call): PASSES. The positive half — without it X3 passes on a harness that fails everything.
- **X5 (containment)** — a call attempting to write outside the scratch root
  (`touch /tmp/outside-marker`) fails the section with a containment finding. The harness must be
  safe to point at arbitrary agent prose; it will one day run in CI against a file someone edited.
  Implement containment by running with `HOME` and `TMPDIR` inside the scratch root and by
  asserting on absolute paths in the call text — state the mechanism in the SUMMARY and be honest
  in it about what the mechanism cannot catch.
- **X6 (result shape)** — `checkSection` returns
  `{ok, section, missing, calls:[{index, line, call, annotations, cwd_before, cwd_after, status, stdout, stderr, findings[]}], engine_version}`.
  Every call is reported whether it passed or failed — a harness that reports only failures cannot
  show a reviewer what it actually ran.

Explicitly NOT in this TRD: `# harness: expect …` annotation semantics, the scratch monorepo,
stub `flutter`/`maestro`/`adb` binaries, `agents/executor.md`, the CI job. All 34-10.
</test_list>

<gotchas>
- **cwd is threaded FORWARD; env is not.** After each call, read the resulting cwd
  (`bash -c '<call>; printf "%s" "$PWD"'` — capture it on a dedicated fd, or append a
  `; pwd > <cwdfile>` epilogue and read the file) and pass it as the NEXT call's `cwd`. Build a
  FRESH `env` object for every call: `{PATH, HOME, TMPDIR}` and nothing else. If you reuse one
  env object and a call exports into it, X3 silently passes.
- **Capturing cwd without corrupting stdout.** Appending `; pwd` to the user's command pollutes
  the captured stdout. Write it to a side file inside the scratch root instead, and read the file
  after `execFileSync` returns — including when it THROWS, because a failing call still changed
  (or did not change) the directory and X1 needs that fact.
- **`set -u` must not break the positive cases.** `set -u` is per-call and applies to the user's
  command; `$PATH` and `$HOME` are set, so nothing legitimate trips. If a real executor block
  trips it in 34-10, that is a FINDING about the prose, not a harness bug — which is the entire
  point.
- **A non-zero exit is not automatically a failure.** The executor's web block contains
  `pgrep chromedriver >/dev/null || { echo CHECKPOINT…; exit 1; }` — a deliberate exit 1. Record
  the status per call and let 34-10's annotations declare the expected one. In THIS TRD, default
  to "non-zero is a finding" and leave `expectedStatus` as an option on the call record.
- **Do not run the caller's shell.** `execFileSync('bash', ['-c', call])` with an explicit
  `shell: false` — never `execSync(call)`, which goes through `/bin/sh` on some platforms and
  through the user's shell semantics on others. The interactive shell on this fleet is zsh; the
  agent's Bash tool is bash. Reproduce bash.
- **Every run is confined.** Create the scratch root with `fs.mkdtempSync`, set `HOME` and
  `TMPDIR` inside it, and `fs.rmSync(root,{recursive:true,force:true})` in an `after()`. A
  harness that leaves directories behind will be disabled within a month.
</gotchas>

<anti_patterns>
- **Do NOT run all calls in one shell.** `bash -c 'call1; call2; call3'` is a different world:
  variables persist, and X3 becomes untestable. One `execFileSync` per call is the model.
- **Do NOT reset cwd to the scratch root between calls.** That is also a different world — it
  would make X1 pass, which is exactly backwards.
- **Do NOT return `{ok: true}` when nothing ran.** E1 and E2. A harness that reports green on a
  section it could not find is the wave-0 lag-check defect with a new name.
- **Do NOT parse bash.** Splitting is line-based with continuation and heredoc handling. A bash
  parser is a project, not a task, and it is not needed: the model is "one line, one call".
- **Do NOT point at a real agent file in this TRD.** Every input is a string in the test file.
- **Do NOT add a dependency** — no `shell-quote`, no `execa`.
</anti_patterns>

<error_recovery>
- If X1 passes when it should fail, your cwd capture is not surviving a call that succeeded — log
  `cwd_before`/`cwd_after` for every call and look for both being the scratch root.
- If X3 passes (i.e. `$REPO_ROOT` resolved), you are reusing an env object or inheriting
  `process.env`. Build the env fresh, per call, from an explicit allow-list.
- If a call hangs, you have an interactive command. Pass a `timeout` to `execFileSync` (10s is
  generous) and report a timeout as a finding, not as a hang.
- If cleanup leaves directories behind after a failing test, register the `after()` hook BEFORE
  the first test that creates a root, and push every root onto a module-level array.
</error_recovery>
