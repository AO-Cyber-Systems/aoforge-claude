# TRD 34-10: the harness meets real prose — scratch monorepo, stubs, annotations, and CI

<objective>

three stub binaries, implement the `# harness:` annotation vocabulary that makes illustrative
prose executable, **make the current `agents/executor.md` Flutter sections pass end-to-end** —
fixing the prose where it does not — and wire a CI job that runs the harness on every PR touching
an agent file.

Resolved intent: kind=plugin, work=feature, tdd=strict, depth=comprehensive,
test_list_first=required, fixture_strategy=generators. Constraints honored:

## Runtime model

Binding for this TRD (OBJECTIVE.md; proposal §21 amendment 2) — and the thing under test.

- **Mirror, not checkout.** Skills invoke `node ~/.claude/devflow/bin/df-tools.cjs` — the MIRROR
  at `~/.claude/devflow`. `executor.md`'s prose names that mirror path, and that is CORRECT prose:
  the harness must not "fix" it to a checkout path. Where a call must actually run, substitute the
  local binary via a `# harness: subst` annotation rather than editing the prose (this is exactly
  what `verifier-ui-eval-invocation.test.cjs:38-42` does: *"Substitute the BINARY, keep the
  ARGUMENTS"*).
- **Bash tool semantics.** cwd PERSISTS across calls; shell variables do NOT; one plain command
  per call under the worktree guard; `( cd "$PACKAGE_DIR" && … )` subshells; evidence paths
  absolute from a per-call `REPO_ROOT`. This TRD asserts all four against the real prose.
- **CommonJS only.** `.cjs`, synchronous `fs`, adjacent tests. **No new npm dependencies.**
  Stub binaries are `#!/usr/bin/env node` scripts or POSIX `sh` scripts, committed executable.
- **Honest output.** A stub that is missing, a section that cannot be located, or a call that
  could not be executed reports `MISSING` with the reason. Never `pass`.

**Annotations (A)**
- **A1** — `# harness: expect <abs-or-root-relative path>` — after the annotated call, the path
  must exist under the scratch root; if not, a finding. Assert both directions.
- **A2** — `# harness: expect-cwd <path>` — the persisted cwd after the call equals the path.
  Combined with 34-09's X1, this lets prose DECLARE an intentional directory change if one ever
  exists, instead of the harness guessing.
- **A3** — `# harness: expect-exit <n>` — the call's status must equal `n`. The `pgrep
  chromedriver || { …; exit 1; }` block is the real consumer: a deliberate exit 1 is correct
  prose and must not read as a failure.
- **A4** — `# harness: derive <VAR>=<value>` — the variable is injected into THAT call's env
  only. A later call without its own `derive` still fails `set -u` (34-09 X3). Assert the
  negative explicitly: `derive` on call 1 does not leak into call 2.
- **A5** — `# harness: subst <token>=<value>` — the literal token is replaced in the call text
  before execution. Used for `<path/to/test.dart>`, `<tests.integration path from TRD>`, and for
  swapping `~/.claude/devflow/bin/df-tools.cjs` for this worktree's binary.
- **A6** — `# harness: skip <reason>` — the call is reported with status `skipped` and the
  reason, and **counts toward `MISSING`, never toward `pass`**. A skip that reads as a pass is
  the whole failure class this program exists to close. Assert that a section containing only
  skips has `ok !== true`.
- **A7** — an UNKNOWN `# harness:` directive is a finding, not a silently-ignored comment. A
  typo'd annotation must not disable a check.

<gotchas>
- **`$(cd X && cmd)` is not a cwd leak.** Command substitution runs in a subshell. 34-09's
  detector works on the OBSERVED cwd after the call, so it should already be correct — but
  `executor.md:177` is the real instance, so confirm it explicitly rather than assuming. If it
  trips, fix the harness with a RED case, not the prose.
- **The `pgrep chromedriver` block exits 1 by design.** `# harness: expect-exit 1`. Flagging it
  as a failure would push someone to "fix" correct prose.
- **`jq` may not be on the CI runner.** `executor.md`'s bootstrap block pipes through `jq`. Either
  add a `jq` stub to the fixture bin, or annotate those calls `# harness: subst` to a node
  equivalent. Decide, and say which in the SUMMARY — a silent "jq: command not found" that the
  harness reports as a finding would make R3 permanently red for an environmental reason.
- **`sed -i` differs between macOS and Linux.** If any prose or test uses it, use a portable form.
  The harness itself must be platform-neutral: CI is ubuntu, developers are macOS.
- **A skip is MISSING, not pass.** A6. The single easiest way to make this harness worthless is a
  `skip` that counts green.
- **R4 before R1-R3.** A green R1 on a section the harness could not parse is the wave-0 lag-check
  defect reproduced inside the tool built to prevent it.
- **R5 must use a COPY.** Never mutate the real `executor.md` in a test, even transiently — a
  crashed test would leave the agent file broken.
- **Path-filtered CI hides red** (fleet memory). Make the job required in the repo settings, or —
  if that is out of band — have the job ALSO run when `.github/workflows/agent-shell-harness.yml`
  itself changes, and note in the SUMMARY that branch protection must list it.
</gotchas>

<anti_patterns>
- **Do NOT give `executor.md` a harness exception.** If a section does not pass, fix the prose.
  The one file this was built for is the one file that must not be exempt.
- **Do NOT make the stubs permissive.** A `flutter` stub that exits 0 for any argument turns
  every prose command into a no-op and every section green. Each stub asserts its arguments.
- **Do NOT copy a real Flutter project into the fixture.** Hand-build the minimum:
  `pubspec.yaml` with a name and an sdk constraint, empty directories, one git commit.
- **Do NOT let `derive` become a shared environment.** A4's negative half. `derive` is a visible,
  per-call declaration; a blanket env would silently make 34-09's X3 unreachable on real prose.
- **Do NOT add `continue-on-error` or `|| true` to the CI step.** C2.
- **Do NOT generalise to other agent files here.** One file, done properly.
</anti_patterns>

<error_recovery>
- If R1-R3 fail, read the finding, then read the prose it names, then decide: prose bug (fix the
  prose, record it) or harness bug (fix the harness with a RED case). Do not add an annotation to
  silence a genuine finding — an annotation is a declaration of intent, not a mute button.
- If R5 passes (the deliberately-broken copy is reported OK), the harness is permissive and R1-R3
  prove nothing. Stop and fix the detector before doing anything else.
- If a stub is invoked with arguments it does not recognise, it should exit non-zero WITH the
  argv it saw. That message is the fastest path from a red R2 to the actual cause.
- If the CI job passes on a branch where you broke the prose, check whether the path filter
  excluded your change, and re-read the fleet memory `path-filtered-ci-hides-red`.
</error_recovery>
