# TRD 34-07: look-lock — writing the acceptance block, and clearing it on shape change only

<objective>
Record a human's approval of a review sheet as a **look-lock** in the spec's own front matter,
and make `ui spec validate` report honestly whether that lock still stands.

§4.1's re-lock rule is the whole design: a change to `routes`, `controls` or `states` clears the
lock; a change to prose does not. This TRD implements exactly that boundary, exposes it as
`df-tools ui lock`, and documents the `look-lock` checkpoint variant the executor runs.

Resolved intent: kind=plugin, work=feature, tdd=strict, depth=comprehensive,
test_list_first=required, fixture_strategy=generators. Constraints honored:
`no_llm_test_data`, `no_property_based_default`, `no_gherkin_layer`.
</objective>

<test_list>
Behaviour cases, written before any test code. Outside-in: the `ui lock` arm (what a human's
approval actually runs), then the shape hash, then the three statuses, then the prose.

**The arm (A)**
- **A1** — `ui lock <spec> --sheet-hash <64 hex> --by mark@aocyber.ai` exits 0, and re-reading
  the spec shows `acceptance.locked_sheet`, `.locked_by`, `.locked_at` (ISO date) and
  `.locked_shape_hash`.
- **A2 (byte-identical prose)** — after `ui lock`, the spec's prose body is **byte-identical** to
  before. Assert on the exact substring after the closing `---`. A YAML rewriter that reflows the
  body has silently edited the artifact a human approved.
- **A3** — `ui lock` on a spec that does NOT validate exits 1 and writes nothing. A signature on
  a broken spec is worse than no signature.
- **A4** — `--sheet-hash` absent, or not 64 hex chars, exits 1 naming the requirement; `--by`
  absent exits 1. `--at` defaults to today and is overridable for deterministic tests.
- **A5** — locking an already-locked spec OVERWRITES the acceptance block (re-lock after a
  change is the normal path) and does not duplicate the keys.

**The shape hash (S)**
- **S1** — `shapeHash(spec)` covers `{routes, controls, states}` and nothing else: two specs
  differing only in `design_read`, `references`, `patterns`, `mode`, `flows`, `scope_rules` or
  the prose body hash IDENTICALLY.
- **S2** — changing a route (adding one, changing a `path`, removing a `back`) changes the hash.
- **S3** — changing a control (adding one, editing a `does`, adding a `behaviors` entry) changes
  the hash.
- **S4** — changing a state (adding one, changing a `seed`, editing `content.must_show`) changes
  the hash.
- **S5** — key-order independence: the same three sections parsed in a different insertion order
  hash identically (canonical, sorted-key serialisation, as in 34-06 H3).
- **S6** — `flows` is deliberately OUTSIDE the hash. §4.1 names only three keys. Pin it as an
  explicit case with a comment, because "flows are surely part of the shape" is the obvious wrong
  intuition and the next person to touch this will have it. If the user disagrees at W1★, it is
  a one-line change with a test that already exists.

**Lock status (L)**
- **L1 (the plan's first RED case)** — `ui lock` writes hash/by/at; immediately afterwards
  `ui spec validate` reports `lock: 'held'`.
- **L2 (the plan's second RED case)** — edit a control, then `ui spec validate` reports
  `lock: 'cleared'` with a reason naming `controls`.
- **L3 (the plan's third RED case)** — edit ONLY the prose body, then `ui spec validate` reports
  `lock: 'held'`. This is the case that makes the lock survivable in practice.
- **L4** — a spec with no `acceptance` block reports `lock: 'absent'`, not `cleared`.
- **L5** — a spec with an `acceptance` block but no `locked_shape_hash` (hand-written, or written
  by an older engine) reports `lock: 'MISSING'` with a reason — never `held`. An undeterminable
  lock is not a valid lock.
- **L6** — `lock: 'cleared'` does not set `ok: false`. Assert `ok === true` on a spec that is
  structurally valid but whose lock is cleared. 34-08 reads the two fields separately.

**Prose (P) — asserted, not reviewed**
- **P1** — `references/checkpoints.md` contains a `look-lock` section; it names
  `df-tools ui lock`, names `sheet_hash`, and states what happens on rejection. Assert by reading
  the file — the same technique `verifier-ui-eval-invocation.test.cjs` uses on `verifier.md`.
- **P2** — every `df-tools` command string appearing in the new `checkpoints.md` and

  does not exist is the wave-0 failure class, one level up.
- **P3** — if this TRD adds any fenced `bash` block to `executor.md`, 34-10's harness suite still
  passes. Run it; do not assume.

Explicitly NOT in this TRD: the `frontend-design` skill (34-08), publishing the sheet, copying
renders into `refs/<surface>/locked/` (a W1★ human step).

<gotchas>
- **Writing YAML back is the risky half of this TRD.** yaml-lite parses; it does not serialise.
  Do NOT round-trip the whole front matter through a serialiser — that would reformat everything
  and destroy the author's layout. Instead do a **surgical text edit**: locate the `acceptance:`
  block in the raw front-matter TEXT (or the end of the front matter, if absent) and
  replace/insert exactly those lines. A2 pins the body; add an assertion that untouched
  front-matter LINES are byte-identical too.
- **`locked_shape_hash` covers three keys, not the whole spec.** S1 and S6. Over-hashing trains
  people to re-approve without reading; under-hashing lets a control change slip past a lock.
- **Three statuses plus MISSING, never two.** `absent` (never locked), `cleared` (locked, shape
  changed), `held` (locked, shape unchanged), `MISSING` (locked but undeterminable). L4 and L5
  exist because collapsing any pair produces a human-facing message that cannot be acted on.
- **`cleared` is not `ok: false`.** L6. A spec can be perfectly valid and un-approved; those are
  different facts and 34-08 needs both.
- **`locked_at` must be injectable.** A test asserting today's date is a test that fails at
  midnight. `--at` defaults to `new Date().toISOString().slice(0,10)` and is overridable.
- **Editing `executor.md` now means 34-10's harness runs your text.** Any fenced bash you add
  needs harness annotations. Prefer adding NO bash to `executor.md` — reference
  `checkpoints.md`'s look-lock section instead. If you must, read `34-10-SUMMARY.md` for the
  annotation vocabulary first.
- **`checkpoints.md` is 908 lines and is loaded by several agents.** Add one focused section;
  do not restructure the file.
</gotchas>

<anti_patterns>
- **Do NOT serialise the whole front matter to write the lock.** Surgical text edit only.
- **Do NOT include `engine_version`, `sheet_hash` or the prose in `locked_shape_hash`.** The
  first would clear every lock on 34-11's version bump; the second is already stored separately;
  the third is exactly what §4.1 says must NOT clear a lock.
- **Do NOT make `cleared` an error.** It is a status. Turning it into `ok: false` makes
  `ui spec validate` unusable as a structural check during authoring, before any sheet exists.
- **Do NOT add a fourth checkpoint type.** `look-lock` is a VARIANT of `checkpoint:human-verify`.
  The three-type taxonomy in `checkpoints.md` is load-bearing for the orchestrator.
- **Do NOT restate the look-lock procedure in `executor.md`.** Document it once in
  `checkpoints.md` and reference it. Two copies of a procedure is the drift class objective 33
  closed.
</anti_patterns>
