# TRD 43-04: Environment and scenario targets get their own key (D4)

<objective>
Stop proposing stack bring-up and scenario scripts as `test`, `e2e` or `build`. Three cases from the fleet, modelled with invented names:

1. eden-biz `make e2e-stack-up` was drafted as `e2e`, but it brings up a live stack. Golden: `e2e_env: make e2e-stack-up`.
2. EdenDocs `wopi-host/scripts/wopi-e2e.sh` was drafted as `build`, because its first classified body line is `go build`. Golden: `e2e: ./wopi-host/scripts/wopi-e2e.sh`.
3. eden-biz `./go/scripts/check-migrations_test.sh` was drafted as the repo-wide `test`. A single-purpose script must be narrow.

Also: aoedge `make acceptance*` are scenario suites, and `build-fips` must still beat `build-dev` (existing canonical rank D25).

Output: a classifier rule, an evidence precedence change, a breadth rule, and e2e shapes.
</objective>

<anti_patterns>
- Adding `e2e_env` to `RUN_POLICY.optInKeys`. Bring-up must never run under `--run`.
- Treating every `*-up` target as `e2e_env`. It needs a scenario token in the name, OR an environment bring-up body signal.
- Letting the name rule demote a script whose name is exactly `test`/`test.sh` to narrow.
- Matching tokens by substring. Use the existing token splitter (`-`, `_`, `:`, `.`), so `setup` doesn't match `up` and `restart` doesn't match `start`.
</anti_patterns>

- If e2e 1 (aocore-shaped, playwright → e2e) changes, the rule is too broad. A plain `e2e` with no env token must stay `e2e`.
